## outline

- Node.js 기반 채팅 서비스를 고도화하는 과정에서 기존 기술 중심 계층형 아키텍처의 한계를 경험
- 이를 실무에서 상황에 맞춰 도메인 주도 설계(DDD)를 적용한 아키텍처로 전환하는 과정을 정리.
- 초기에는 단순성과 빠른 개발을 위해 기술 중심의 계층형 아키텍처를 채택하여 사용
- **기존 기술 중심의 계층형 아키텍처를 도메인 중심 구조로 재구성**하여 비즈니스 도메인별로 응집된 구조를 확보
- 기능 간의 **관심사 분리와 책임 명확화**를 통해 유지보수성, 확장성, 테스트 용이성을 향상

## 1. 기술 중심의 계층형 아키텍처의 구조적 제약
- 디렉토리가 controller, service, model 등 **기술적인 역할을 기준으로 구성**
- 동일 도메인에 속한 구성 요소가 **여러 디렉토리에 분산되어 응집도가 낮음**
- **기능 수정** 또는 신규 기능 추가 시 관련 코드가 여러 위치에 흩어져 있어 변경 범위가 넓고 파악에 시간이 소요됨

> UserController.js, UserService.js, User.js가 각각 controllers, services, models 디렉토리에 흩어져 있음
>
> 예시 구조: 
>
> ```css
> src/
> ├── controllers/
> │   └── UserController.js	← Express 요청 핸들러
> ├── services/
> │   └── UserService.js		← Sequelize 모델 (DB 정의)
> ├── models/
> │   └── User.js						← 비즈니스 로직 처리
> ...
> ```

## 2. 기술 중심 구조의 한계점

### 초기 장점

- 익숙한 구조 덕분에 소규모 프로젝트에서는 빠른 개발이 가능하고 진입 장벽이 낮음

### 성장에 따른 문제점

1. **응집도 및 재사용성 저하**
   - 도메인별로 책임이 분산되고 명확한 경계가 없기 때문에 **유사하거나 중복되는 로직이 여러 레이어에 산재**되어 있음.
   - 이는 **중복 구현**, **로직 분산**, **일관성 저하**, **재사용 어려움**, **버그 발생 가능성** 등의 문제로 이어지고 있음.
2. **유지보수성 및 확장성 저하**
   - 구조가 기술 책임 중심에 머물러 있어 **비즈니스 복잡성을 효과적으로 반영하지 못함**
   - 도메인별 코드가 여러 계층에 나뉘어 있어 **흐름 파악 및 영향 분석에 높은 비용** 발생
   - **구조적 복잡성으로 인해 신규 개발자 온보딩이나 기능 이해에 높은 진입 비용** 발생

---

| 항목                   | 기술 중심 구조       | DDD 기반 구조                      |
| ---------------------- | -------------------- | ---------------------------------- |
| **비즈니스 로직 위치** | Service에 흩어짐     | 도메인 내부에 응집                 |
| **설계 기준**          | 기능/DB 테이블 중심  | 도메인 개념 중심                   |
| **유지보수성**         | 낮음                 | 높음                               |
| **테스트 용이성**      | 낮음                 | 높음                               |
| **확장성**             | 모놀리틱, 비대해짐   | 도메인 단위 확장 용이              |
| **표현력**             | 기술적 구성요소 중심 | 의미 중심(Entity, Value Object 등) |

## 3. 패키지 구조 변경: 기술 중심 → 도메인 중심 아키텍처

### Before: 기술 중심 계층형 구조

```css
src/
├── controllers/
│   └── UserController.js     ← Express 요청 핸들러
├── models/
│   └── User.js               ← Sequelize 모델 (DB 정의)
├── services/
│   └── UserService.js        ← 비즈니스 로직 처리
├── routes/
...
```

### **⚠️ 문제점 요약**

- **기술 책임별로 나뉜 구조로, 도메인 개념이 코드 구조에 반영되지 않음**
- **도메인 단위로 코드를 추적하거나 재사용하기 어려움**
- **`User.js`는 DB 모델, 도메인 모델(Entity), 데이터 접근 로직까지 혼재되어 역할이 명확히 분리되지 않음.**
- **`UserService.js`는 도메인 로직과 유스케이스 로직이 뒤섞여 있어 역할 간 책임 분리가 미흡.**
- **테스트, 유지보수, 신규 도메인 기능 확장 시 코드 탐색 및 영향도 파악이 어렵고, 변경 비용이 높음**

### After: 도메인 중심 아키텍처

```css
src/
├── domains/                           ✅ 도메인 로직 중심
│   └── user/
│       ├── User.js                    ← 도메인 엔티티
│       ├── UserService.js             ← 도메인 서비스 (비즈니스 로직)
│       ├── UserRepository.js          ← 도메인 저장소 인터페이스
│       └── UserEvents.js              ← 도메인 이벤트 정의
├── application/                       ✅ 유스케이스 계층 (비즈니스 시나리오 조율자)
│   └── user/
│       └── UserApplicationService.js  ← 유스케이스 처리 (트랜잭션 단위)
├── infrastructure/                    ✅ 외부 기술 연동 (ORM, Redis 등)
│   ├── persistence/
│   │   └── UserRepositoryImpl.js      ← Sequelize 기반 저장소 구현
│   └── caching/
│       └── UserCache.js               ← Redis 기반 캐시 구현
├── interfaces/                        ✅ 입출력 인터페이스 분리 (Express, gRPC, Socket)
│   ├── routes/
│   │   ├── HttpRouter.js              ← RESTful HTTP 요청 라우팅 처리
│   │   ├── GrpcRouter.js              ← gRPC 프로토콜 라우팅 처리
│   │   └── SocketRouter.js            ← 실시간 Socket 이벤트 라우팅 처리
│   └── UserController.js              ← HTTP 핸들러 (Express 컨트롤러)
...
```

### 개선 사항 및 이점

| 항목                                  | 개선 내용                                                    |
| ------------------------------------- | ------------------------------------------------------------ |
| **도메인 응집력 향상**                | 도메인별로 관련 요소가 한 곳에 모여 관리, 이해 및 유지보수 효율성 향상 |
| **책임 분리 명확화**                  | I/O 처리, 유스케이스 조율, 도메인 로직 구현이 계층별로 명확히 구분됨 |
| **인프라와 도메인의 분리**            | `UserRepositoryImpl`, `UserCache`는 기술 구현에 종속되고, 도메인은 이를 의존하지 않음 → 테스트 용이성 및 기술 교체 유연성 확보 |
| **테스트 유연성 확보**                | 인터페이스 기반 설계로 Mocha, Chai, Sinon 등을 활용한 Stub/Mock 기반 테스트 구현 용이 |
| **확장성과 마이크로서비스 전환 용이** | 도메인 단위 모듈화로 향후 마이크로서비스 또는 모듈 분리 구조로 확장 가능 |
| **DDD 설계 원칙 준수**                | Entity, Value Object, Repository, Service, UseCase 등 Tactical Pattern이 명확히 적용됨 |
